# Lesson 140 — Cross-Site Scripting (XSS)

## 1. What is XSS?

**Cross-site scripting (XSS)** happens when an application treats attacker-controlled content as executable code in another user's browser.

Example: a shopping website displays product reviews. An attacker submits content that the website accidentally interprets as HTML/JavaScript instead of text. When another user opens the page, unwanted code may run in that user's browser.

**Main rule:** User-generated text is **data**, not trusted HTML or JavaScript.

## 2. Why is it dangerous?

An XSS vulnerability can let malicious script:
- Act as the logged-in user in the browser.
- Read page data and non-HttpOnly browser storage.
- Send requests using the user's browser session.
- Change page content or show a fake login form.

**Important:** An `HttpOnly` cookie cannot be read by JavaScript, but XSS may still make authenticated requests from the affected browser. HttpOnly helps but does not fix XSS.

## 3. Three common types

| Type | What happens? | Example |
| --- | --- | --- |
| **Stored XSS** | Malicious content is saved and shown later | Comment stored in MongoDB |
| **Reflected XSS** | Input is immediately included in a response | Search term printed into unsafe HTML |
| **DOM-based XSS** | Frontend JavaScript inserts untrusted data unsafely | Assigning query-string content to `innerHTML` |

### Stored XSS flow

```text
Attacker submits malicious-looking comment
  -> backend stores it in MongoDB
  -> another user loads comments
  -> frontend renders comment as HTML (unsafe)
  -> browser may interpret it as active content
```

Saving a string in MongoDB is not the vulnerability by itself. **Unsafe rendering** creates the problem.

## 4. Unsafe vs safe browser rendering

```js
// BAD: treats untrusted text as HTML
commentContainer.innerHTML = reqComment;

// GOOD: treats it as plain text
commentContainer.textContent = reqComment;
```

For example, if the comment contains `<b>Hello</b>`, `textContent` displays those literal characters, while `innerHTML` interprets the tag.

## 5. React and Next.js examples

React escapes text expressions by default:

```jsx
function Comment({ text }) {
  return <p>{text}</p>; // Safe text rendering
}
```

Avoid using untrusted content directly in:

```jsx
// BAD when html comes from users and has not been safely sanitized
<div dangerouslySetInnerHTML={{ __html: html }} />
```

If your app **must** support rich HTML, use a maintained HTML sanitizer with a strict allowlist of permitted tags and attributes before rendering. Sanitization must fit the rendering context and be kept updated. Do not invent a regex that only strips `<script>` tags.

React escaping helps for normal text, but it does not make arbitrary URLs, unsafe HTML injection, or direct DOM manipulation safe automatically.

## 6. Output encoding: context matters

The correct protection depends on **where** the value is placed:

| Context | Preferred approach |
| --- | --- |
| Text inside HTML | Framework text escaping or `textContent` |
| HTML attribute | Framework safe binding + attribute validation |
| URL | Validate allowed protocols and destinations |
| JavaScript code | Do not interpolate untrusted strings into executable code |
| Rich HTML | Strict HTML sanitization + safe rendering |

Example: before putting a user-provided link into `href`, allow only expected protocols (such as `https:`) and approved destinations when appropriate. Escaping alone does not make dangerous URL schemes safe.

## 7. Express example: API data vs unsafe HTML

A JSON API returning user text is not automatically XSS. The risk appears when the frontend renders that text unsafely.

```js
app.get("/comments", async (req, res) => {
  const comments = await Comment.find()
    .select("text author")
    .lean();
  res.json({ comments });
});
```

Frontend:

```jsx
{comments.map((comment) => (
  <p key={comment._id}>{comment.text}</p>
))}
```

Use schema validation to limit text size and reject invalid types, but **validation alone does not replace output encoding**.

## 8. Content Security Policy (CSP)

A **CSP** tells the browser which sources of scripts, styles, images, and other resources are allowed. It provides an **additional layer**, not a replacement for safe rendering.

With Helmet (see Lesson 143):

```js
import helmet from "helmet";
app.use(helmet());
```

A strict CSP can reduce XSS impact, but real policies must account for your scripts, nonces/hashes, external services, and deployment. Avoid relying on `unsafe-inline` for scripts where possible. Test CSP with `Content-Security-Policy-Report-Only` before enforcing complex policies.

## 9. Cookies, tokens, and XSS

- `HttpOnly` prevents JavaScript from directly reading a cookie.
- `Secure` restricts cookies to secure connections (HTTPS, with browser-specific localhost exceptions).
- `SameSite` helps against some cross-site request scenarios.
- None of these settings fixes an XSS vulnerability.
- Avoid storing long-lived sensitive tokens in JavaScript-readable storage when a safer session design is available.

## 10. Common mistakes

1. Assuming MongoDB automatically removes dangerous HTML.
2. Rendering untrusted strings with `innerHTML`.
3. Assuming `HttpOnly` makes XSS harmless.
4. Treating input validation as equivalent to HTML encoding.
5. Assuming React makes `dangerouslySetInnerHTML` safe.
6. Copying a CSP that breaks the app, then disabling it entirely.

## 11. Practice

1. Build a comments list that renders user text safely in React.
2. Compare `textContent` and `innerHTML` using a harmless `<b>Hello</b>` string.
3. Explain why a comment saved in MongoDB can become stored XSS only when displayed unsafely.
4. Add a CSP in report-only mode and inspect browser console warnings.

## Interview-ready answer

XSS is when untrusted content becomes executable code in a user's browser. Stored, reflected, and DOM-based XSS differ in where unsafe content enters the page. Prevent XSS with safe text rendering, context-aware output encoding, validated URLs, carefully sanitized rich HTML, and CSP as defense in depth.
