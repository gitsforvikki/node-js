# Lesson 123 — JWT

## Why JWT is heavily asked in interviews

JWT is easy to use incorrectly.

Interviewers often ask:

- What is JWT?
- What are its three parts?
- Is JWT encrypted?
- How is it verified?
- Where should JWT be stored?
- Access token vs refresh token?
- How do you revoke JWT?
- HS256 vs RS256?
- What should go in the payload?
- What are common JWT vulnerabilities?

This lesson covers both concept and production practice.

---

## 1. What is JWT?

JWT stands for:

```text
JSON Web Token
```

It is a compact token format commonly used to carry signed claims.

Typical use:

```text
Client
   |
   v
JWT access token
   |
   v
API
   |
   v
verify signature + claims
```

---

## 2. JWT structure — where is the signature stored?

A common **signed JWT** contains **three parts separated by dots**:

```text
header.payload.signature
  1      2       3
```

Example **shape** (not a real usable token):

```text
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMDEifQ.exampleSignature
```

- **Header** = token metadata, for example which signing algorithm is used.
- **Payload** = claims, such as the user ID and expiry.
- **Signature** = cryptographic proof that helps the server detect unauthorized changes.

**Where is the signature saved?** It is **already the third part of the complete JWT**. When the server sends the token to a client, the signature travels with the header and payload. Normally the signature is **not saved separately in the database**.

**Very important:** The **signing key / JWT_SECRET is not inside the JWT**. It remains securely on the server (or in a secret manager). Anyone with the token can see its three parts, but they should not be able to create a new valid signature without the appropriate signing key.

```text
SERVER:  Header + Payload + signing key
                     |
                     v
             Create signature
                     |
                     v
         Header.Payload.Signature
                     |
                     v
                  CLIENT
```

JWT payload ko readable samjho; JWT signing ko encryption mat samjho.
---

## 5. Signature — why is it needed, and what exactly is inside?

Suppose the server issues:

```json
{ "userId": 101, "role": "user" }
```

An attacker changes the **payload** to:

```json
{ "userId": 101, "role": "admin" }
```

**Question:** Agar payload readable hai, to attacker admin kyu nahi ban sakta?

**Answer:** Signature is calculated from the encoded header and payload **using a trusted signing key**. If a payload/header changes, its old signature will no longer match. Without the key the attacker cannot normally create a replacement valid signature.

### HS256 signature kaise banta hai?

Conceptually:

```text
signingInput = base64url(header) + "." + base64url(payload)

signature = base64url(
  HMAC-SHA256(signingInput, JWT_SECRET)
)
```

Signature me **password, full user details, ya JWT_SECRET stored nahi hota**. It contains the **cryptographic result** of signing the encoded header and payload. (Other signing algorithms such as RS256 use a different calculation.)

### Actual JWT creation in Node.js

Install: `npm install jsonwebtoken`.

```js
import jwt from "jsonwebtoken";

// Only after checking the user's login password successfully:
const token = jwt.sign(
  { sub: String(user.id), role: "user" },
  process.env.JWT_SECRET,
  { algorithm: "HS256", expiresIn: "15m" }
);

console.log(token); // header.payload.signature
```

Here `JWT_SECRET` is a strong, randomly generated **server-side** secret. Do **not** return it to the client, put it in a JWT payload, or commit it to GitHub.

### Server signature verify kaise karta hai?

```http
GET /api/profile
Authorization: Bearer <JWT_TOKEN>
```

Server checks:

1. Extract full JWT (including its signature).
2. Use its **trusted secret** to validate the signature (the library handles safe cryptographic verification).
3. Check token expiry and other expected claims.
4. Apply a **separate authorization check** for the requested resource.

```js
try {
  const payload = jwt.verify(token, process.env.JWT_SECRET, {
    algorithms: ["HS256"],
    // Set issuer and audience here when your tokens use them.
  });

  console.log(payload.sub); // authenticated subject
} catch {
  // Reject missing, modified, expired, or otherwise invalid tokens.
}
```

`jwt.verify()` checks integrity and configured claims; **`jwt.decode()` does not verify**. Never use decoded-but-unverified claims to trust a user's identity.

```text
           JWT arrives at server
                    |
                    v
         Verify signature and claims
                 /      \
             valid      invalid
               |           |
               v           v
       Check permissions   Reject
               |
               v
          Allow / Deny
```

### JWT signature vs JWT_SECRET

| JWT signature | JWT_SECRET (HS256) |
| --- | --- |
| Third part of the token | Secret signing key held by server |
| Visible to the client | Never sent to client |
| Depends on signed header/payload + key | High-entropy random secret |
| Travels in every JWT | Kept in secure server config/secret store |
| Not normally saved separately | Protected and rotated when needed |

**HS256:** same secret is used to sign and verify. **RS256:** a **private key** signs, while a **public key** verifies. The public verification key can be shared, but the private signing key stays secret.

## 6. JWT is usually signed, not encrypted

**Signing and encryption are different things.** Common signed JWTs (JWS) are **Base64URL encoded, not encrypted**. Anyone holding the token can usually decode the header and payload without knowing the secret key.

- **Signing** provides integrity/authenticity: did the content change, and was it signed by a trusted key?
- **Encryption** provides confidentiality: can an unauthorized person read the content?
- **JWE (JSON Web Encryption)** is a different JWT form that can encrypt content. `jsonwebtoken.sign()` creates a **signed** JWT, not a JWE.

| Question | Signed JWT (JWS) | Encryption / encrypted JWT (JWE) |
| --- | --- | --- |
| Can someone holding it read the payload? | Usually **yes** | Not without a decryption key |
| Main job | Detect tampering, prove valid signer | Keep content confidential |
| What does it protect? | Integrity/authenticity | Confidentiality (with authenticated encryption, integrity too) |
| Default `jsonwebtoken.sign()`? | Yes | No |

**Bad payload — NEVER put secrets here:**

```json
{
  "password": "hello123",
  "creditCard": "4111..."
}
```

**Better:**

```json
{
  "sub": "101",
  "role": "user"
}
```

Keep claims minimal. A role in a valid JWT can still become outdated when a user's permissions change, so sensitive authorization should check fresh permissions where appropriate.

### What if an attacker steals a valid JWT?

**Signature does NOT prevent use of a stolen valid bearer token.** A thief holding a still-valid bearer token may send it as-is; they do not need to change the payload.

Use HTTPS, short token lifetime, safe client storage, careful refresh-token handling and revocation where needed.

**Remember:** `Base64URL encoding != encryption`, and `valid signature != permission to access everything`.

## 10. Token issuance flow — complete login example

Why issue JWT at all? After a successful login, you don't want to send the user's email and password with every API request. A short-lived signed access token is **one option** (server-side sessions are another).

```text
1. User sends email + password -> POST /login
2. Server finds user and verifies submitted password against stored hash
3. If valid, server signs access token with user ID + short expiry
4. Client receives the complete JWT (header.payload.signature)
5. Client sends JWT with later authorized API requests
```

```js
// In a login handler, after user exists and password comparison succeeds:
const token = jwt.sign(
  { sub: String(user.id) },
  process.env.JWT_SECRET,
  { algorithm: "HS256", expiresIn: "15m" }
);

res.json({ accessToken: token });
```

Password verification happens with a password-hashing library, **not JWT**. Do not store password or password hash inside the token.

## 11. Request verification flow — subsequent API call

```http
GET /api/profile
Authorization: Bearer <JWT_TOKEN>
```

```text
Client sends entire JWT
          |
          v
Server extracts Bearer token
          |
          v
Verify signature + exp (+ iss / aud as appropriate)
          |
     +----+----+
     |         |
   Valid     Invalid
     |         |
     v         v
Check access  401 Reject
     |
     v
Return authorized data (or 403 Deny)
```

**Never** treat Base64URL decoding as authentication. A user may also have a valid token yet lack permission to access another user's order. Authentication and authorization are different checks.

## 12. Decode vs verify

Decode:

```text
read payload
```

Verify:

```text
validate cryptographic signature
+
validate claims
```

Never use decode-only output as authenticated identity.

---

## 13. HS256

HS256 uses a shared secret.

```text
same secret
  -> signs
  -> verifies
```

Useful for simpler architectures.

Risk:
every verifier with secret can also sign tokens.

---

## 14. RS256

RS256 uses asymmetric keys.

```text
private key
   -> sign

public key
   -> verify
```

Useful when many services need to verify tokens but should not be able to mint them.

---

## 15. Symmetric vs asymmetric mental model

```text
HS256
  one shared secret

RS256
  private signing key
  public verification key
```

---

## 16. Algorithm allowlist

Never blindly accept whatever algorithm the token header requests.

Verification code should explicitly allow expected algorithms.

This protects against algorithm-confusion style vulnerabilities.

Browser apps may store auth tokens in:

## 19. localStorage trade-off

Storing access token in localStorage makes it accessible to JavaScript.

If XSS occurs, attacker may steal token.

This is why browser token storage deserves careful design.

## 23. Why not make access token last 30 days?

Because if stolen, attacker gets 30 days of access.

Short access tokens reduce the theft window.

## 24. JWT revocation challenge

A self-contained signed token remains cryptographically valid until expiration.

So:

```text
user logs out
```

does not magically invalidate every JWT unless architecture supports revocation.

Possible approaches:

- short TTL
- token denylist
- token version
- session record
- refresh-token revocation

## 25. Token version

User:

```json
{
  "tokenVersion": 4
}
```

JWT:

```json
{
  "sub": "123",
  "ver": 4
}
```

If user resets password:

```text

```

Old tokens with version 4 can be rejected if server checks DB/state.

Trade-off:
now verification is not fully stateless.

## 27. Do not overstuff JWT

Bad:

```json
{
  "sub": "123",
  "name": "...",
  "email": "...",
  "permissions": ["hundreds..."],
  "preferences": {...}

```

Problems:
- token gets large
- stale claims
- sensitive info exposure

## 30. JWT Express example

Using a mature JOSE/JWT library conceptually:

```js
const token =
  await signAccessToken({
    sub: user.id,
    role: user.role,
  });
```

Verification middleware:

```js
const payload =
  await verifyAccessToken(
    token
  );

req.auth = payload;
```

Then authorization is separate.

## 31. JWT secret quality

For HMAC algorithms, use a strong random secret.

Bad:

```text
secret123
```

Good:

```text
cryptographically random high-entropy value
```

Store it in secret management/environment configuration.

## 32. Secret rotation

Production systems eventually rotate keys/secrets.

Useful mechanism:

```text
kid
```

in JWT header identifies which key signed the token.

Verifier can support old + new keys during migration.

---

## 33. Issuer validation

Expected:

```text
iss = auth.example.com
```

Without issuer validation, a token signed by the same trusted key for another context might be accepted incorrectly.

---

## 34. Audience validation

Expected:

```text
aud = careerloop-api
```

Audience ensures token is intended for your service.

---

## 35. Clock skew

Distributed servers may have slight clock differences.

Libraries often allow a small tolerance.

Do not set huge clock tolerance that defeats expiration semantics.

---

## 36. Logout with JWT

If access token is short-lived:

```text
logout
   |
   v
delete client credential
   |
   v
revoke refresh session
   |
   v
access token expires soon
```

For immediate high-risk revocation, maintain server-side state.

## 37. JWT is not automatically stateless auth

If you use:
- refresh-token DB
- denylist
- session records
- token versions

then the system uses server-side state.

That is perfectly valid.

Do not optimize for "stateless" at the expense of security.

## 38. CSRF vs XSS

Token in cookie:


Token in JS-accessible storage:


JWT:


## 43. Interview questions — clear answers

### Q: Is JWT encrypted or signed?
Typically signed. The common three-part signed JWT (JWS) has readable Base64URL-encoded header/payload. Encrypted JWTs (JWE) also exist.

### Q: What are the three parts?
**Header.Payload.Signature**. The signature is the token's third part, not a separate database field.

### Q: What does the signature contain?
A **cryptographic result** calculated using the encoded header/payload and the signing key. It is not a storage location for the key, password or user details.

### Q: Where is the signing secret stored?
On the **server**, ideally in a secret manager or protected environment configuration — never inside the JWT or frontend bundle.

### Q: Can an attacker change role=user to role=admin?
They can edit an encoded payload, **but signature verification fails** unless they can produce a valid new signature with the signing key.

### Q: What if an attacker steals a valid JWT?
They may be able to use it as a bearer token until it expires or is revoked. Signature alone does not prevent replay/theft.

### Q: Decode vs verify?
Decode **reads** the payload. Verify **checks** the signature and relevant claims such as expiry. Never authenticate using decode-only output.

### Q: HS256 vs RS256?
HS256 uses the same secret for signing and verification. RS256 uses a private signing key and public verification key.

### Q: What should be in JWT payload?
Only minimal, non-sensitive claims (for example `sub`). Do not put passwords, payment details or secrets inside.

### Q: How do you revoke JWT?
Possible choices: short access-token lifetime plus refresh-session revocation, denylist, token-version checks or server-side session state.

### Q: Does a valid JWT automatically authorize access?
No. Verify the token **then** check whether that user may access the requested resource.
---

## 44. Strong interview answer

> JWT is a compact signed token format made of a Base64URL-encoded header, payload, and signature. The payload is readable and should not contain secrets. On every request I verify the signature and important claims such as expiration, issuer, audience, and allowed algorithm rather than merely decoding the token. I prefer short-lived access tokens and use server-side refresh-session state or token versioning for revocation. Authentication from the JWT is still separate from resource-level authorization.
