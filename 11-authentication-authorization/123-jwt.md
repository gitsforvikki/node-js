# Lesson 123 — JWT

## Why JWT is heavily asked in interviews

JWT is easy to use incorrectly.

Interviewers often ask:

- What is JWT?
- What are its three parts?
- Is JWT encrypted?
- How is it verified?
- Where should JWT be stored?
- Access token vs refresh token?
- How do you revoke JWT?
- HS256 vs RS256?
- What should go in the payload?
- What are common JWT vulnerabilities?

This lesson covers both concept and production practice.

---

## 1. What is JWT?

JWT stands for:

```text
JSON Web Token
```

It is a compact token format commonly used to carry signed claims.

Typical use:

```text
Client
   |
   v
JWT access token
   |
   v
API
   |
   v
verify signature + claims
```

---

## 2. JWT structure

A JWT commonly has three Base64URL-encoded sections:

```text
header.payload.signature
```

Example shape:

```text
xxxxx.yyyyy.zzzzz
```

---

## 3. Header

Example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

It describes token metadata such as signing algorithm.

---

## 4. Payload

Example:

```json
{
  "sub": "user_123",
  "role": "user",
  "iat": 1710000000,
  "exp": 1710000900
}
```

Payload contains claims.

---

## 5. Signature

Conceptually:

```text
base64url(header)
+
"."
+
base64url(payload)
   |
   v
sign with secret/private key
   |
   v
signature
```

The signature detects tampering.

---

## 6. JWT is usually signed, not encrypted

Critical interview point:

Anyone holding the token can usually decode header and payload.

So never put secrets inside JWT payload.

Bad payload:

```json
{
  "password": "...",
  "creditCard": "..."
}
```

Signature provides integrity/authenticity, not confidentiality.

---

## 7. Standard claims

Common claims:

```text
sub -> subject
iss -> issuer
aud -> audience
exp -> expiration
nbf -> not before
iat -> issued at
jti -> JWT ID
```

---

## 8. Subject

Usually:

```text
sub = user ID
```

Example:

```json
{
  "sub": "usr_123"
}
```

Prefer stable internal identity.

---

## 9. exp

Expiration prevents indefinite token validity.

Example:

```text
access token:
15 minutes
```

Exact duration depends on risk model.

Short-lived access tokens reduce exposure.

---

## 10. Token issuance flow

```text
Login
  |
  v
verify credentials
  |
  v
create claims
  |
  v
sign JWT
  |
  v
return/store token
```

---

## 11. Request verification flow

```text
Request
   |
   v
extract token
   |
   v
verify signature
   |
   v
verify exp/iss/aud/etc
   |
   v
read trusted claims
   |
   v
authorization
```

Do not simply decode and trust.

---

## 12. Decode vs verify

Decode:

```text
read payload
```

Verify:

```text
validate cryptographic signature
+
validate claims
```

Never use decode-only output as authenticated identity.

---

## 13. HS256

HS256 uses a shared secret.

```text
same secret
  -> signs
  -> verifies
```

Useful for simpler architectures.

Risk:
every verifier with secret can also sign tokens.

---

## 14. RS256

RS256 uses asymmetric keys.

```text
private key
   -> sign

public key
   -> verify
```

Useful when many services need to verify tokens but should not be able to mint them.

---

## 15. Symmetric vs asymmetric mental model

```text
HS256
  one shared secret

RS256
  private signing key
  public verification key
```

---

## 16. Algorithm allowlist

Never blindly accept whatever algorithm the token header requests.

Verification code should explicitly allow expected algorithms.

This protects against algorithm-confusion style vulnerabilities.

---

## 17. JWT in Authorization header

Common:

```http
Authorization: Bearer <access-token>
```

Good for:
- APIs
- mobile clients
- service clients

---

## 18. JWT in HTTP-only cookie

Browser apps may store auth tokens in:

```text
HttpOnly cookie
```

Benefits:
- JavaScript cannot directly read it
- reduces token theft through some XSS paths

But cookie-based auth introduces CSRF considerations.

---

## 19. localStorage trade-off

Storing access token in localStorage makes it accessible to JavaScript.

If XSS occurs, attacker may steal token.

This is why browser token storage deserves careful design.

---

## 20. Cookie security flags

Important:

```text
HttpOnly
Secure
SameSite
```

Example:

```js
res.cookie(
  "accessToken",
  token,
  {
    httpOnly: true,
    secure: true,
    sameSite: "lax",
  }
);
```

Actual SameSite choice depends on cross-site architecture.

---

## 21. Access token

Access token should usually be:

- short-lived
- used on API requests
- limited in scope/claims

Example:

```text
15 minutes
```

---

## 22. Refresh token

Refresh token is used to obtain a new access token.

It should usually be:

- longer-lived
- more strongly protected
- revocable
- rotated

Refresh-token design is covered later in this section.

---

## 23. Why not make access token last 30 days?

Because if stolen, attacker gets 30 days of access.

Short access tokens reduce the theft window.

---

## 24. JWT revocation challenge

A self-contained signed token remains cryptographically valid until expiration.

So:

```text
user logs out
```

does not magically invalidate every JWT unless architecture supports revocation.

Possible approaches:

- short TTL
- token denylist
- token version
- session record
- refresh-token revocation

---

## 25. Token version

User:

```json
{
  "tokenVersion": 4
}
```

JWT:

```json
{
  "sub": "123",
  "ver": 4
}
```

If user resets password:

```text
tokenVersion -> 5
```

Old tokens with version 4 can be rejected if server checks DB/state.

Trade-off:
now verification is not fully stateless.

---

## 26. jti

`jti` gives a unique token ID.

Useful for:
- revocation lists
- audit
- replay detection

---

## 27. Do not overstuff JWT

Bad:

```json
{
  "sub": "123",
  "name": "...",
  "email": "...",
  "permissions": ["hundreds..."],
  "preferences": {...}
}
```

Problems:
- token gets large
- stale claims
- sensitive info exposure
- bandwidth overhead

Keep claims minimal.

---

## 28. Role in JWT?

Possible:

```json
{
  "role": "admin"
}
```

Works well if role changes infrequently and access token is short-lived.

For sensitive authorization, you may still check fresh DB permissions.

---

## 29. JWT payload is not source of truth forever

Suppose role changed from admin to user.

Old token may still say:

```text
admin
```

until expiration.

This is why short TTL and authorization strategy matter.

---

## 30. JWT Express example

Using a mature JOSE/JWT library conceptually:

```js
const token =
  await signAccessToken({
    sub: user.id,
    role: user.role,
  });
```

Verification middleware:

```js
const payload =
  await verifyAccessToken(
    token
  );

req.auth = payload;
```

Then authorization is separate.

---

## 31. JWT secret quality

For HMAC algorithms, use a strong random secret.

Bad:

```text
secret123
```

Good:

```text
cryptographically random high-entropy value
```

Store it in secret management/environment configuration.

---

## 32. Secret rotation

Production systems eventually rotate keys/secrets.

Useful mechanism:

```text
kid
```

in JWT header identifies which key signed the token.

Verifier can support old + new keys during migration.

---

## 33. Issuer validation

Expected:

```text
iss = auth.example.com
```

Without issuer validation, a token signed by the same trusted key for another context might be accepted incorrectly.

---

## 34. Audience validation

Expected:

```text
aud = careerloop-api
```

Audience ensures token is intended for your service.

---

## 35. Clock skew

Distributed servers may have slight clock differences.

Libraries often allow a small tolerance.

Do not set huge clock tolerance that defeats expiration semantics.

---

## 36. Logout with JWT

If access token is short-lived:

```text
logout
   |
   v
delete client credential
   |
   v
revoke refresh session
   |
   v
access token expires soon
```

For immediate high-risk revocation, maintain server-side state.

---

## 37. JWT is not automatically stateless auth

If you use:
- refresh-token DB
- denylist
- session records
- token versions

then the system uses server-side state.

That is perfectly valid.

Do not optimize for "stateless" at the expense of security.

---

## 38. CSRF vs XSS

Token in cookie:

```text
better protected from JS theft
but browser auto-sends cookie
-> think about CSRF
```

Token in JS-accessible storage:

```text
not auto-sent cross-site
but XSS can read it
```

There is no magic storage location with zero trade-offs.

## 39. Common JWT attacks/mistakes

### Mistake 1
Decode without verify.

### Mistake 2
No expiration.

### Mistake 3
Weak secret.

### Mistake 4
Sensitive payload data.

### Mistake 5
No issuer/audience validation.

### Mistake 6
Accepting arbitrary algorithms.

### Mistake 7
Very long access tokens.

### Mistake 8
No refresh-token revocation strategy.

---

## 40. JWT vs session

JWT:

```text
claims carried in token
easy distributed verification
revocation harder
stale claims possible
```

Session:

```text
server stores session state
easy immediate revocation
requires shared session store at scale
```

Neither is universally better.

---

## 41. When JWT fits well

Useful when:

- multiple APIs need verification
- mobile/API clients
- distributed services
- short-lived access tokens
- asymmetric signing

---

## 42. When session may be simpler

Good for:

- traditional web apps
- centralized backend
- easy logout/revocation
- minimal client token handling

---

## 43. Interview questions

### Is JWT encrypted?

Usually no. It is signed and Base64URL encoded.

### What are the three JWT parts?

Header, payload, signature.

### Decode vs verify?

Decode only reads claims. Verify checks cryptographic integrity and claims.

### HS256 vs RS256?

HS256 uses shared secret; RS256 uses private key for signing and public key for verification.

### How do you revoke JWT?

Short TTL plus server-side mechanisms such as refresh-session revocation, denylist, token version, or session record.

### What should be in JWT payload?

Minimal non-sensitive claims needed for authentication/authorization.

---

## 44. Strong interview answer

> JWT is a compact signed token format made of a Base64URL-encoded header, payload, and signature. The payload is readable and should not contain secrets. On every request I verify the signature and important claims such as expiration, issuer, audience, and allowed algorithm rather than merely decoding the token. I prefer short-lived access tokens and use server-side refresh-session state or token versioning for revocation. Authentication from the JWT is still separate from resource-level authorization.
